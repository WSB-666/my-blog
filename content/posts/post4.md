# 仿真里四行代码就能飞，为什么真机非要一整套 Nav2？——聊聊"导航"的两副面孔

> ROS2 学习笔记 · 导航的两副面孔
> 2026-10-16

---

## 引子

这周我干了两件看似毫不相干的事：

一边在写比赛代码——让一架仿真里的无人机从 A 飞到 B；
一边在啃 ROS2 的导航教程——Nav2，一堆不认识的名词。

然后我卡在一个很朴素的困惑上：

- 比赛里，让无人机从 A 飞到 B，我核心就写了几行控制代码；
- 可 Nav2 光"真正干活的节点"就有八个，还有代价地图、TF 链、粒子滤波一大堆。

**同样是"从 A 飞到 B"，凭什么差这么多？**

是我比赛里写得太简陋，还是 Nav2 把简单问题搞复杂了？

这周我想明白了。结论先放这儿：

> **导航的复杂度，不是由"移动"决定的，而是由"不确定性"决定的。**

下面把这句结论拆开讲。

---

## 一、先看"简单"的那副面孔：仿真里的"导航"

比赛仿真里，我要让无人机飞到一个目标点，做的就一件事：**算误差，然后按误差给速度。**

核心五步：

1. **读位姿** —— 从 `/flight_control/current_pose` 拿当前 (x, y, z, yaw)
2. **算误差** —— 目标减当前，得到 `ex / ey / ez / yaw_error`
3. **比例控制 + 限幅** —— 误差乘个系数当速度，再夹住上限
4. **旋到机体系** —— `/cmd_vel` 要的是"机身自己的前后左右"，不是世界的
5. **进死区就停** —— 误差小于几厘米，干脆发零速度

写成代码大概这样：

```python
# 误差
ex, ey = target_x - x, target_y - y
ez     = target_z - z
yaw_err = wrap_to_pi(target_yaw - yaw)

# 世界系速度 = 比例控制 + 限幅
world_vx = clamp(0.8 * ex, -0.28, 0.28)
world_vy = clamp(0.8 * ey, -0.28, 0.28)
vz       = clamp(0.9 * ez, -0.25, 0.25)
w        = clamp(1.2 * yaw_err, -0.6, 0.6)

# /cmd_vel 要机体系速度，按当前朝向转一下
vx =  world_vx * cos(yaw) + world_vy * sin(yaw)
vy = -world_vx * sin(yaw) + world_vy * cos(yaw)
```

就这些。没有地图、没有路径、没有躲障碍——**它笔直朝目标点冲过去，误差一大就报错？不存在的。**

⚠️ **但请注意第 1 步：这个位姿是"真值"。**

仿真的插件（`ican_delivery_gazebo_uav_simple_move`）订阅我的 `/uav/cmd_vel`，把速度积分一遍，**直接把无人机的确切位置算出来发到 `/uav/odom`**。中间那个飞控桥接节点，只是把 `/uav/odom` 搬成 `/flight_control/current_pose` 转发给我。

也就是说——

> **我的"导航"里，最难的那部分（定位），被仿真白送了。**

我拿到的永远是"我确切在哪"，于是我只需要回答"差多少、给多少速度"。

---

## 二、再看"复杂"的那副面孔：真机上要回答的五个问题

把真机摆进来，同样是"从 A 飞到 B"，问题立刻变成五个：

| # | 问题 | 仿真里 | 真机上 |
|---|---|---|---|
| 1 | **我在哪？** | 白送真值 | 只有会漂的里程计，得估计 |
| 2 | **周围有什么？** | 环境已知、静态 | 事先不知道，得边看边建 |
| 3 | **该走哪条路？** | 直线怼过去 | 不能怼，要规划绕行 |
| 4 | **怎么走不撞？** | 撞了再说 | 实时避障 |
| 5 | **谁保证都按顺序起来？** | 我自己手敲命令 | 得有一套编排机制 |

**Nav2，就是对这五个问题的"标准答案"。**

它不是把简单问题搞复杂了——它是把仿真帮你省掉的那些问题，一个个补了回来。

---

## 三、Nav2 的一条数据流

不管 Nav2 内部有多少节点，对外其实就一条流：

```
/scan ──→ AMCL ──→ Planner ──→ Controller ──→ /cmd_vel ──桥接──→ 轮子
(看到墙)  (知道         (规划怎么      (算转多少弯、
          我在哪)        走)            走多快)
```

对应到 5 个关键话题：

| 步骤 | 话题 | 一句话 |
|---|---|---|
| 感知 | `/scan` | 前方 X 米有墙 |
| 里程计 | `/odom` | 我走到 (x, y) 了 |
| 地图 | `/map` | 这里是空地，那里是墙 |
| 路径 | `/plan` | 从这到那，走这条路 |
| 速度 | `/cmd_vel` | 左转 0.3，前进 0.2 |

**看这条流，最大的感受是：它把我的"读位姿 → 算速度"给撑开了。**

我的几行代码，在 Nav2 里对应的是中间那一长串——因为真机没法直接"读位姿"。

---

## 四、八个节点，各管一摊

把上面那条流拆成节点，真正干活的其实就这几个：

| 节点 | 职责 |
|---|---|
| **map_server** | 加载保存的地图，发布 `/map` |
| **amcl** | 激光 + 里程计 → 定位，发布 map→odom |
| **planner_server** | 生成全局路径，发布 `/plan` |
| **controller_server** | 跟路径 + 避障，输出 `/cmd_vel` |
| **behavior_server** | 恢复行为（原地转、后退、清地图） |
| **bt_navigator** | 行为树，调度上面几个 |
| **velocity_smoother** | 速度平滑 |
| **lifecycle_manager** | 按顺序把节点从 unconfigured 拉到 active |

> [!note] 别被 35 个节点吓到
> 跑起来 `ros2 node list` 会刷出一大串，但大部分是生命周期管理的子节点，以及每个导航节点自带的 TF 监听器。核心就是上面这 8 个。

对比一下第一节我那五步——**"读位姿 → 算速度"在这张表里，被拆成了 amcl + planner + controller 三个节点。** 差得不是一点半点。

---

## 五、RViz 里那层粉色的东西：代价地图

第一次开 Nav2，RViz 里墙边围着一圈**粉色**。当时我以为是什么渲染 bug，后来才知道那叫**代价地图（Costmap）**。

我建的地图（`/map`）只有黑白：墙是黑，空地是白。它回答"哪里有障碍"，但不回答"**哪里能走**"。

代价地图是在黑白地图上又叠了一层"安全区"：

| 颜色 | 含义 |
|---|---|
| 深/黑 | 已知障碍物，绝对不能走 |
| **粉/紫** | 膨胀区——障碍物周围的"危险缓冲带" |
| 白/浅 | 安全空地 |

**为什么要这层粉色？**

因为车有宽度，不是质点。贴着墙走一定会蹭到。膨胀层等于给每堵墙"套了一圈安全距离"，规划器算路径时会自动绕开粉色区，保证车体不碰墙。

```yaml
inflation_layer:
  inflation_radius: 0.35   # 膨胀半径（米）
  cost_scaling_factor: 3.0 # 衰减系数，越大粉色圈越紧贴墙
```

它分两张：

| 类型 | 话题 | 范围 | 用途 |
|---|---|---|---|
| 全局代价地图 | `/global_costmap/costmap` | 整张地图 | planner 算全局路径 |
| 局部代价地图 | `/local_costmap/costmap` | 车周围一小圈 | controller 实时避障 |

**这一节让我意识到**：我仿真里那个"撞了再说"的写法，在真机上根本不成立——真机得先有"危险区"的概念。

---

## 六、AMCL：机器人"不太确定自己在哪"

真机上，机器人其实**不知道自己在哪**。

它只知道里程计说"我从起点转了 3 圈、往前走了 5 米"——但轮子会打滑，这个数是会漂的。

于是 Nav2 用 **AMCL**（自适应蒙特卡洛定位）来解决：撒一堆**粒子**，每个粒子都代表一个"我可能在这儿"的猜测，用激光数据和地图一匹配，猜得准的粒子留下、猜得偏的淘汰。

怎么看出来它还不确定？看 RViz：**机器人周围散着一堆粉色小点，就是粒子云。粒子越集中，说明定位越准。**

⚠️ **一个新手必踩的坑**：启动导航后，必须在 RViz 里点一下 **2D Pose Estimate**，给它一个初始位置猜测。不点的话，粒子会随机乱撒，定位不收敛，地图上机器人的位置会乱跳。

> **这一节是全文的关键**：AMCL 那堆粒子，本质就是在说一句话——"我不确定我在哪，所以我给你一堆可能性。"

而我的仿真里，从来没有这句话，因为我拿到的就是真值。

## 七、两副面孔，一张表

把两边的对应关系摆在一起：

| 要解决的事 | 仿真里（我的比赛代码） | 真机上（Nav2） |
|---|---|---|
| 我在哪 | Gazebo 直接给真值位姿 | AMCL 粒子滤波**估计** |
| 周围环境 | 已知、静态 | 激光实时感知 + 建图 |
| 怎么走 | 直线飞向坐标点 | planner 算全局路径 |
| 避障 | 没有 | 代价地图膨胀 + controller |
| 谁编排 | 我自己按顺序敲命令 | bt_navigator + lifecycle_manager |

**一眼能看出来：仿真那一列，几乎每一项都是"免费"的。**

不是因为我写得简陋，而是因为问题本身在仿真里就被消掉了。

---

## 八、钥匙其实是"定位"两个字

如果只准我说一个词，来解释这两副面孔的差距——

**定位。**

- 仿真：**真值** → 确定性 → 所有下游问题都跟着变简单
- 真机：**估计** → 带着误差 → 所有下游问题都得"在误差里求解"

一旦"我在哪"变成了一个有误差的估计，后面的路径规划、避障、控制，全都得把这份不确定性考虑进去。这就是 Nav2 那一整套存在的理由。

---

## 九、什么时候该用哪副面孔

这周想通之后，我给自己定了条很简单的判断：

**先问"不确定性有多少"，再决定"栈要有多厚"。**

| 场景 | 该用哪副 |
|---|---|
| 位姿是现成的、环境已知、目标只是一个坐标点 | 简单控制就够，**别上 Nav2** |
| 位姿要估计、环境要感知、目标是个"不能撞的区域" | **才需要 Nav2** |

我以前总觉得"工具越全越专业"。现在反过来想：**在不缺确定性的场景里硬搬全套，反而是负担。** 工具是跟着问题走的，不是反过来。

（这个道理，其实和我上一篇写无人机模型时悟到的是同一件事：无人机是刚体，所以不需要关节，也就不需要 ros2_control 那套。）

## 十、这周遗留的问题

老实说，这周是"看得懂流程图，细节还啃不动"。

具体卡在哪：

1. **我的 fly_to 只是"位姿伺服"** —— 一旦目标点被墙挡住（这周就撞过一次窗框旁的实心墙），它不会自己绕路。这恰好反证了：**我没有 planner**。
2. **官方其实给了 navigation 包** —— 入口话题 `/uav/fly_to`，但练习环境没装，我只能自己写。真机版里它怎么做的局部避障，我还没看。
3. **AMCL 的粒子权重** —— 只知道"匹配得好就留下"，具体的概率更新过程没啃。

**所以下周计划**：把 AMCL 那套概率更新搞明白，顺便看看官方 navigation 包的接口设计。

## 写在最后

如果用一句话总结这两副面孔：

> **导航不是在"控制怎么动"，而是在"回答我到底在哪、世界长什么样"。**

仿真把这两个答案直接塞给了我，所以我只需要几行 P 控制；
真机上没人体贴地给答案，所以 Nav2 才长成了八个节点的样子。

**不确定性，才是导航复杂度的真正来源。**
